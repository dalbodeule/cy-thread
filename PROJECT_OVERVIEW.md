# mori.space 프로젝트 현황

> 기준: 2026-10-03 현재 저장소 코드와 설정. 이 문서는 구현된 동작, 운영에 필요한 설정, 아직 남은 작업을 한곳에 정리한다. 외부 서비스의 실제 설정 상태와 배포 상태는 코드만으로 증명할 수 없으므로 별도로 확인해야 한다.

## 1. 서비스 구조

`mori.space`는 관심사별 커뮤니티 서비스다. 구조는 **Forum → Category(게시글 모음) → Thread(게시글) → Post(본문·댓글)** 순서다. 홈은 전체 Forum과 활동을 보여주고, Forum별 페이지에서 카테고리를 고르거나 게시글을 읽고 작성한다.

| 영역      | 현재 구성                                                                                                             |
| --------- | --------------------------------------------------------------------------------------------------------------------- |
| 웹        | Nuxt 4, Vue 3, Tailwind CSS 및 공통 스타일. 웹 페이지와 서버 API가 한 Worker에서 동작한다.                            |
| 실행      | Cloudflare Workers, Nitro `cloudflare_module` 프리셋. 운영 도메인은 `community.mori.space`로 설정돼 있다.             |
| 데이터    | Cloudflare D1(SQLite) + Drizzle ORM. 스키마와 SQL 마이그레이션은 `server/db/`에 있다.                                 |
| 파일      | Cloudflare R2 `community` 버킷. 게시글 이미지와 업로드 프로필 사진을 저장한다.                                        |
| 로그인    | Google OAuth, CHZZK OAuth, `nuxt-auth-utils` 세션 쿠키.                                                               |
| 메일      | Cloudflare Email Sending `EMAIL` 바인딩, 기본 발신 주소 `webmaster@mori.space`.                                       |
| 예약 작업 | 매시 정각 인기 카테고리 갱신과 미사용·삭제 게시물 첨부 및 참조되지 않는 업로드 아바타 정리, 매분 발송 대기 메일 처리. |

주요 설정은 [`nuxt.config.ts`](nuxt.config.ts), [`wrangler.toml`](wrangler.toml), [`package.json`](package.json)을 참고한다. 현재 코드와 Wrangler 개발 환경은 D1을 사용하며, 이전 Neon 데이터베이스는 더 이상 연결하지 않고 그 데이터도 D1로 이전하지 않았다.

## 2. 사용자 기능과 화면

| 기능        | 화면·동작                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 홈·탐색     | `/`에서 이름순 공개 Forum 최대 100개, 최근 활동순 공개 Thread 12개, 인기 카테고리 최대 8개를 본다. 추천 카테고리가 아직 계산되지 않았으면 공개 카테고리 중 앞의 8개를 대신 표시한다. Forum 목록 검색도 이 최대 100개 범위에서 동작하며 추가 페이지는 없다. `/explore`에서 카테고리 이름·slug로 공개 카테고리를 검색하고 Forum으로 필터링하며, 30개씩 더 불러온다. Forum 필터 목록은 동일하게 이름순 공개 Forum 최대 100개다.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Forum       | `/forums/<slug>/threads`에서 Forum 소개, 카테고리, 검색·정렬·페이지네이션, 팔로우, 게시글 목록을 본다. 멤버 수는 소유자·Forum 관리자·중재자·승인 멤버·팔로워와 삭제되지 않은 Thread 작성자 및 그 안의 미삭제 Post 작성 계정을 중복 없이 합산한다. 승인 멤버가 아닌 로그인 사용자도 댓글을 작성했다면 포함되며, 계정이 없는 게스트 작성자는 제외된다. 전체 관리자라는 역할만으로는 별도로 포함되지 않는다. 공개/비공개 가입 승인 설정, 첫 방문 안내, 규칙, 키워드 차단 규칙과 운영 자료실 링크를 지원한다.                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 게시글·댓글 | 게시글 작성·수정·삭제, 질문·투표·공지, 태그, 2단계 댓글, 반응, 글 구독, 읽음 위치 저장, 조회수, 공유와 신고를 지원한다. 조회수는 브라우저 탭 세션마다 Thread별 한 번 기록하며 상세와 Forum·홈 최근 글 목록에 표시한다. Thread 제목·메타데이터는 `threads` 행에, 본문은 부모가 없는 첫 `posts` 행에 저장하며 댓글도 `posts` 행으로 저장한다. 글 상세는 본문 Post와 댓글을 합쳐 100개씩 DB에서 내려받는다. `#post-ID` 링크는 본문 Post나 댓글이 로드될 때까지 추가 페이지를 불러온다. 로그인 사용자는 현재 로드된 마지막 Post ID를 저장하며 더 보기 후 갱신한다. 읽음 위치를 화면에 표시하거나 이어 읽기에 활용하는 UI는 아직 없다. 본문과 댓글은 Toast UI 편집기를 사용한다. Thread를 삭제하면 Thread와 본문·댓글 Post 모두 소프트 삭제되며, 본문 Post는 단독 삭제할 수 없다. 댓글만 삭제하면 해당 댓글만 소프트 삭제한다. 첨부 D1 행과 신고 이력은 소프트 삭제 후 보존한다. 삭제된 Post 이미지는 제공하지 않으며 R2 객체는 30일이 지난 뒤 시간별 정리 작업에서 삭제한다. |
| Forum 개설  | `/forums/request`에서 신청한다. 전체 관리자가 승인해야 Forum과 기본 카테고리가 생성된다. 승인 후에는 1주일간 새 신청이 제한된다. 반려할 때는 관리자가 재신청을 1주일 제한할지 선택할 수 있다.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| 프로필      | `/account/profile`에서 이름과 사진을 관리하고 최근 알림(최대 50개)·작성 활동(미삭제 게시글 최대 50개, 댓글 최대 100개)·소유·Forum 관리자·팔로우 Forum·공개 Forum에 저장한 글(최대 100개)을 본다. 비공개 Forum 글도 권한이 있으면 북마크할 수 있지만 프로필의 저장 목록에는 나타나지 않는다. Forum 목록은 소유·Forum 관리자·팔로우 관계를 합치고 중복을 제거하며, 중재자 역할만 가진 Forum은 포함하지 않는다. JSON 내보내기는 계정 정보와 최신 작성 Thread 최대 1,000개, Post 최대 5,000개, 신고 최대 1,000개를 포함하며, 소프트 삭제된 레코드도 작성자 기준 조회 결과에 포함될 수 있다. 사용자 차단과 Forum 뮤트도 제공한다. 공개 프로필은 공개 Forum의 미삭제 Thread 최대 30개와 댓글 최대 50개를 노출하며 본문 Post는 포함하지 않는다. Gravatar는 확인된 이메일이 필요하다.                                                                                                                                                                                            |
| 이메일 확인 | CHZZK가 이메일을 제공하지 않으므로 `/account/email`에서 연락 주소를 입력하고 메일 링크로 확인한다. Google의 로그인 이메일과 별도로 저장된다.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 에러 화면   | [`app/error.vue`](app/error.vue)가 400, 401, 404, 500 상태별 안내와 이동·재시도 동작을 제공한다. API는 기존 오류 응답을 유지한다.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

공통 헤더·계정 메뉴·바닥글은 `app/components/SiteTopbar.vue`, `HeaderAccountActions.vue`, `SiteFooter.vue`와 [`app/app.vue`](app/app.vue)에서 구성한다. 좁은 화면에서는 사이트 헤더와 Forum 헤더 모두 햄버거 버튼으로 오른쪽 슬라이드 메뉴를 열며, 메뉴 바깥을 누르거나 링크를 따라가면 닫힌다. Forum은 별도 브랜드와 사각형 아이콘·색상 설정을 헤더에 반영한다. White/Dark/System 테마가 있으며 Forum 관리자가 다크 모드를 끄면 해당 Forum의 테마 선택기가 숨겨지고 밝은 테마를 사용한다. 전역 검색은 공개 Forum의 글만 대상으로 한다.

## 3. 권한과 관리자 기능

| 역할                         | 가능한 작업                                                                                                                                                         |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 방문자                       | 공개 Forum과 게시글 읽기.                                                                                                                                           |
| 로그인 사용자                | 게시글·댓글 작성, 팔로우, 신고, Forum 개설 신청, 본인 프로필 관리, 게시글 북마크 저장·조회.                                                                         |
| Forum 운영진(`mod`)          | 신고 처리, 게시글 잠금·고정 등 운영 작업과 회원 제재.                                                                                                               |
| Forum 관리자(`admin`)·소유자 | 운영진 권한에 더해 카테고리, Forum 설정, Forum 대상 메일을 관리한다. 소유자·전체 관리자는 Forum 관리자를, 소유자·Forum 관리자는 중재자를 임명·해제할 수 있다.       |
| 전체 관리자                  | Forum 개설 신청 승인·거절, 전체 사용자·Forum 관리, 전체·Forum·선택 사용자 대상 메일을 관리한다. Forum 운영 권한을 가지며 Forum 관리자·중재자를 임명·해제할 수 있다. |

- 전체 관리자 화면: `/admin`, `/admin/forum-requests`, `/admin/users`, `/admin/mail`. 헤더의 **관리도구** 버튼으로 들어간다.
- 사용자 목록은 이름·이메일·작성글·댓글을 검색하고 페이지네이션한다. 사용자 상세에서 최근 활동과 제재 기록을 본다. 정지는 30분, 1시간, 6시간, 1일, 7일, 1개월, 영구 중 선택하고 해제할 수 있다. 전체 관리자 계정과 실행자 본인은 정지할 수 없으며, 정지 중에는 로그아웃을 제외한 인증된 API 쓰기 요청이 차단된다.
- Forum 관리 화면: `/forums/<slug>/admin`, 하위 `categories`, `settings`, `users`, `mail`; 신고 검토는 `/forums/<slug>/reports`다.
- 중재자는 Forum 관리자 계정이나 다른 중재자 계정을 제재할 수 없다. Forum 관리자 계정의 임명·해제와 제재는 소유자 또는 전체 관리자만 할 수 있으며, 소유자와 전체 관리자는 중재자 계정도 관리할 수 있다. Forum 운영진은 소유자나 전체 관리자를 제재할 수 없다.
- 카테고리에 Thread가 남아 있으면 같은 Forum의 다른 카테고리를 지정해야 한다. 소프트 삭제된 Thread를 포함해 모든 해당 Thread 행을 이동하며, 본문·댓글 Post는 Thread에 그대로 연결된다.
- 화면의 버튼 노출과 별개로 서버의 `requireGlobalAdmin`·`requireForumModerator` 및 각 API가 권한을 검사한다. 세부 권한은 [`server/utils/requireForumModerator.ts`](server/utils/requireForumModerator.ts)와 `server/api/admin/`, `server/api/forums/[slug]/moderation/`에 있다.

## 4. 게시글 검색과 파일

- 게시글은 D1에 저장하며 제목·본문 검색, 카테고리·고정·잠금 필터, 정렬 및 페이지네이션을 제공한다. FTS5 색인과 트리거는 [`0006_post_search_fts.sql`](server/db/migrations/0006_post_search_fts.sql)에서 만들고, 제목 갱신 트리거는 [`0017_repair_threads_fts_trigger.sql`](server/db/migrations/0017_repair_threads_fts_trigger.sql)에서 다시 정의한다.
- 본문 이미지 업로드는 JPEG/PNG/GIF/WebP, 최대 5 MB다. 서버가 파일 서명을 확인하고 R2에 저장한 뒤 D1 `attachments` 행을 만든다. 게시글에 연결되기 전 이미지는 Forum 접근 권한이 있는 업로더에게만 보인다. 연결된 이미지는 Forum의 공개 범위와 게시글 삭제 상태를 요청할 때마다 확인한다. 공개 Forum 이미지만 공개 Cache API에 캐시한다.
- 이미지 요청은 같은 R2 버킷에서 공개 Forum 이미지, 비공개 Forum 이미지, 아직 게시글에 연결되지 않은 업로드를 구분해야 하므로 현재 권한 확인 API를 거친다. 공개 Cache API가 게시된 공개 이미지를 캐시한다. R2 custom domain은 해당 도메인으로 버킷 객체를 공개할 수 있어 현재 혼합 버킷에 바로 연결하지 않는다. 직접 CDN 전달을 적용하려면 공개 객체만 별도 버킷으로 분리하고 custom domain을 연결한 뒤 이관·권한 검증이 필요하다([Cloudflare R2 public buckets](https://developers.cloudflare.com/r2/buckets/public-buckets/)).
- Forum 운영진은 **24시간이 지난 미사용 업로드**를 수동으로 정리할 수 있다. 예약 작업은 매시 정각 미사용 첨부를 최대 100개씩 정리하며, 글에서 이미지를 제거하면 첨부를 미사용 상태로 바꾸고 24시간 유예 후 삭제한다. 소프트 삭제된 게시글·댓글에 연결된 이미지는 삭제 시각부터 30일이 지나면 매시간 최대 100개씩 정리한다. R2 삭제나 D1 메타데이터 정리에 실패하면 시각을 기록하고 6시간 후 다시 시도해 실패한 객체가 매번 정리 배치의 앞부분을 차지하지 않게 한다. 업로드 아바타는 이전 사진 교체 시 삭제를 시도하고, 전체 `avatars/` 경로의 미참조 객체는 cursor 페이지네이션으로 찾아 정리한다. 현재 사용 중인 파일은 삭제 대상에서 제외한다. 삭제 전에 생성된 백업 스냅샷에는 이미지 사본이 남을 수 있으며, 정기 실행이 정상일 때 백업 보존 기간까지 포함한 최대 보관은 대략 60일이다.
- 프로필 업로드는 JPEG/PNG/WebP, 최대 2 MB다. 새 사진으로 전환한 뒤 이전 R2 파일 삭제를 시도하며, 삭제 실패나 다른 이유로 현재 계정이 참조하지 않는 업로드 아바타는 매시 정각 예약 작업이 R2 전체 `avatars/` 경로를 페이지 단위로 확인해 정리한다. 공급자 사진과 Gravatar는 외부 URL이며 이 서비스의 R2 파일이 아니다.

관련 코드: [`attachments.post.ts`](server/api/forums/%5Bslug%5D/attachments.post.ts), [`cleanup.post.ts`](server/api/forums/%5Bslug%5D/moderation/attachments/cleanup.post.ts), [`avatar.post.ts`](server/api/account/avatar.post.ts).

## 5. 운영 메일

전체 관리자는 `/admin/mail`에서 전체 사용자, 특정 Forum 대상자 또는 선택한 사용자에게 메일 캠페인을 등록할 수 있다. 선택 사용자 발송은 캠페인당 최대 500명이다. Forum 소유자·관리자는 자신의 Forum 대상자에게만 보낼 수 있다. Forum 대상자는 팔로워, 소유자·운영진(Forum 관리자·중재자), 삭제되지 않은 Thread·Post 작성자이며 승인 멤버 자격만으로는 포함되지 않는다. 캠페인 대상은 메일 수신 설정이 켜져 있고 기본 이메일 또는 확인된 연락 이메일이 있어야 한다. 작성 화면에는 안내 양식, 수신 대상, 미리보기와 미완성 `{{...}}` 항목 검사 기능이 있다. 실제 발송 전 확인 단계를 거쳐 분 단위 처리 대기열에 등록한다. 미래 발송 시각을 지정하는 기능은 없다.

서버는 메일을 D1 대기열에 넣고, 매분 예약 작업에서 대상자 최대 100명을 확장하고 최대 10건을 발송한다. 따라서 큰 캠페인은 여러 분에 걸쳐 처리된다. 대상 확장 시점에 수신 설정과 기본 이메일 또는 확인된 연락 이메일을 확인해 주소를 대기열에 저장하며, 발송 직전에는 수신 설정을 다시 확인해 해제된 사용자는 건너뛴다. 주소 자체는 발송 직전에 다시 조회하지 않는다. 발송 실패는 최대 5회 시도하며 재시도 간격은 1·2·4·8분이다. 다섯 번째 실패는 실패 상태로 남고 캠페인은 오류 완료로 표시된다. HTML과 일반 텍스트 본문을 함께 생성한다. 제재 안내와 CHZZK 연락 이메일 확인 메일도 같은 발송 경로를 쓴다. 단체 메일에는 수신 거부 페이지 링크와 이메일 클라이언트가 처리할 수 있는 원클릭 수신 거부 헤더가 붙는다. 기본 발신자는 `wrangler.toml`의 `MAIL_FROM_ADDRESS`로 바꿀 수 있다.

관련 코드: [`MailComposer.vue`](app/components/MailComposer.vue), [`createMailCampaign.ts`](server/utils/createMailCampaign.ts), [`renderMail.ts`](server/utils/renderMail.ts), [`server/plugins/mail.ts`](server/plugins/mail.ts).

## 6. 보안과 데이터 보호

- 현재 로그인 콜백은 DB에 저장된 OAuth 토큰을 읽지 않으며 access/refresh token을 D1에 기록하지 않는다. CHZZK 콜백은 공급자가 반환한 access token을 사용자 정보 조회에 메모리에서만 사용한다. `oauth_accounts` 스키마와 초기 마이그레이션에는 레거시 nullable 토큰 열이 남아 있으므로, 운영 DB에 기존 값이 없는지는 별도로 확인해야 한다. 세션은 서명·암호화된 HTTP 전용 쿠키를 사용한다. CHZZK 연락 이메일은 확인 전까지 로그인 식별자나 Google 계정 연결 근거가 아니다.
- Turnstile은 Forum 개설 신청, 게시글·댓글 작성, 신고, 비공개 Forum 가입 신청, 게시글 본문 이미지 업로드에서 검증한다. 프로필 사진 업로드에는 Turnstile 검증이 없다. Worker Rate Limiting 바인딩은 Forum·카테고리 목록, Forum 글 목록·상세 조회와 인증된 쓰기·이미지 업로드·신고·운영 작업 등에 적용된다. Thread 조회수 POST도 사용자 ID 또는 IP를 키로 읽기 제한(분당 120회)을 적용한다. 비회원이 허용된 Forum에서 작성하는 댓글 등 인증되지 않은 쓰기 요청은 일반 쓰기 Rate Limiting 바인딩을 적용하지 않는다. 읽기 제한도 모든 GET API에 적용되는 것은 아니다. 적용 대상에서 익명 요청은 `cf-connecting-ip` 헤더가 없으면 제한을 건너뛴다. 설정된 바인딩의 `limit()` 호출이 실패하면 로그를 남기고 요청을 허용하지만, 프로덕션에서 바인딩이 없으면 503을 반환한다(일반 개발 모드는 제한을 건너뛴다). 제한 값은 [`wrangler.toml`](wrangler.toml), 요청 분류는 [`server/middleware/security.ts`](server/middleware/security.ts)에 있다.
- 백업용 별도 Worker·Workflow 코드는 [`backup/`](backup/)에 있다. 설정된 일정은 매일 한국 시간 02:00(UTC 17:00)이며 D1 내보내기와 R2 `forums/` 객체(Forum 첨부)를 스냅샷으로 저장한다. 스냅샷 날짜와 prefix는 예약 이벤트 시각의 UTC 날짜를 사용하므로 한국 시간 02:00 실행은 한국 달력 기준 전날 날짜로 기록된다. `avatars/`의 업로드 프로필 사진은 백업 대상이 아니다. 성공한 실행은 UTC 스냅샷 날짜 기준 정확히 31일 전의 prefix를 정리하므로, 만료일의 예약 실행이 누락되면 31일보다 오래된 스냅샷이 남을 수 있다. **저장소에 코드가 있다는 사실만으로 백업 Worker 배포·정상 실행·복구 가능성이 확인되지는 않는다.** 배포 후 첫 실행의 `manifest.json`과 실제 복구 연습을 별도로 확인해야 한다.
- Cloudflare Workers Logs 및 429·5xx 관측 코드가 구성돼 있다. 로그 설정과 보관 기간은 실제 계정 설정에서 확인한다.
- 동적 사이트맵은 공개 Forum 최대 10,000개와 공개·미삭제 게시글 중 ID가 큰 순서로 최대 30,000개를 포함한다. `robots.txt`의 명시적 차단 목록은 로그인·계정·메일·관리 경로와 Forum 신고 경로다. 별도로 `nuxt.config.ts`의 `robots: false` route rule은 해당 경로 응답에 `X-Robots-Tag: noindex, nofollow`를 설정하지만, `disallowNonIndexableRoutes` 기본값이 꺼져 있어 route rule 경로를 `robots.txt` 차단 목록에 자동 추가하지 않는다. 팔로우 피드·사용자 프로필·Forum 신청·이메일 확인·수신거부 페이지는 페이지 메타에도 `noindex, nofollow`를 설정한다. 관련 설정은 [`nuxt.config.ts`](nuxt.config.ts), [`urls.get.ts`](server/api/__sitemap__/urls.get.ts), 각 페이지의 `useSeoMeta` 호출에 있다.

## 7. 개발·배포 요약

```sh
npm install
npm run db:migrate:local
npm run dev:worker
```

`npm run dev`는 일반 Nuxt 개발 서버다. D1·R2 등 Worker 바인딩이 필요한 흐름은 `npm run dev:worker`를 사용한다. 로컬 미리보기 데이터가 필요하면 `npm run db:seed:local`을 실행한다.

운영 배포 순서는 **마이그레이션 확인 → 빌드 → Worker 배포**다.

```sh
npm run db:migrate:remote
npm run build
npx wrangler deploy .output/server/index.mjs --assets .output/public
```

필요한 비밀 값은 `NUXT_SESSION_PASSWORD`, `NUXT_TURNSTILE_SECRET_KEY`, 사용 중인 OAuth 공급자의 `NUXT_OAUTH_GOOGLE_CLIENT_ID`·`NUXT_OAUTH_GOOGLE_CLIENT_SECRET` 및 `NUXT_OAUTH_CHZZK_CLIENT_ID`·`NUXT_OAUTH_CHZZK_CLIENT_SECRET`이다. 공개 Turnstile 키는 `NUXT_PUBLIC_TURNSTILE_SITE_KEY`다. 값은 저장소에 쓰지 않고 Worker secret/variable 또는 로컬 `.dev.vars`에 둔다. OAuth 공급자에도 운영 콜백 주소를 정확히 등록해야 한다. Wrangler 로그인 상태라면 일반 배포·D1 마이그레이션에 별도 API 토큰은 필요하지 않다. 백업 Worker의 D1 REST API 호출은 별도 토큰이 필요하다.

첫 전체 관리자는 신뢰할 수 있는 계정으로 로그인한 뒤 D1의 `users.is_global_admin`을 운영자가 직접 설정해야 한다. 그 이후 Forum 개설 승인과 전체 관리자 기능은 해당 계정에서 처리한다. 백업 Workflow는 별도 배포가 필요하며, 스냅샷 날짜는 실행 이벤트의 UTC 날짜다. 성공할 때 UTC 스냅샷 날짜 기준 31일 전의 prefix를 정리한다. 만료일의 실행이 누락되면 오래된 스냅샷이 남을 수 있다. 배포·복구 절차의 상세 명령은 [`README.md`](README.md)의 **Backups and recovery** 및 **Cloudflare setup** 절을 따른다.

## 9. 다른 커뮤니티와 비교한 기능 목표

2026-09-29 기준 [Discourse의 사용자 안내](https://meta.discourse.org/t/understanding-discourse-for-new-users/96331/1), [GitHub Discussions의 기능 안내](https://docs.github.com/en/discussions/collaborating-with-your-community-using-discussions/about-discussions), [Reddit의 운영 도구 안내](https://support.reddithelp.com/hc/en-us/articles/15484384020756-Moderation-Tools-overview)를 비교했다. 현재도 Forum·카테고리·게시글·댓글, Forum 안의 검색, 팔로우, 신고·운영 기능은 갖추고 있다(2~4절). 이들은 서로 다른 규모와 목적의 서비스이므로 모든 기능을 그대로 복제할 필요는 없다. 아래 우선순위와 제안은 **mori.space의 공개 Forum 중심 구조에 맞춘 판단**이다. '없음'은 현재 화면·API·DB 스키마에서 확인되지 않는다는 뜻이며, 외부 운영 설정의 상태까지 단정하지 않는다.

## 10. 추가 목표: Web Push 알림

### 10.1 검토 결론

**적용 가능하다.** 현재 스택(Nuxt 4, Cloudflare Worker, D1)에 Web Push를 추가할 수 있으며, 이미 구현한 인앱 `notifications` 테이블을 알림의 원본으로 두고 브라우저 푸시는 보조 전달 채널로 붙이는 구성이 적절하다. Push API는 서비스 워커가 필요하고 구독 결과에 엔드포인트와 암호화 키가 포함된다([MDN Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)). 구독 요청은 HTTPS 환경과 사용자 동작을 전제로 하며 VAPID 공개 키를 `applicationServerKey`로 사용한다([MDN PushManager.subscribe](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe)).

운영 도메인(`community.mori.space`)이 HTTPS로 제공되므로 브라우저 측 전제는 충족할 수 있다. 다만 현재 저장소에는 서비스 워커와 Web Push 구독 저장·발송 코드가 없으므로 **아직 적용 완료 상태는 아니다.** 모바일 브라우저와 Safari를 포함한 실제 기기별 동작은 별도 검증이 필요하다. Notifications API는 권한과 서비스 워커 알림 표시가 필요하고 브라우저별 지원 범위가 다르다([MDN Notifications API](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API)).

### 10.2 필요한 구성

| 구성        | 계획                                                                                                                                                                                                                                                                                                                                                                  |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 브라우저    | `public/sw.js`에서 `push` 이벤트를 받아 `showNotification()`으로 표시하고, 알림 클릭 시 원래 Forum 글 URL을 연다. 권한 요청과 `PushManager.subscribe()`는 사용자가 버튼을 누른 뒤 실행한다.                                                                                                                                                                           |
| 비밀 값     | VAPID 공개 키는 클라이언트 설정으로 노출하고, 개인 키는 Worker secret으로 저장한다. VAPID는 애플리케이션 서버를 식별·인증하기 위한 서명 토큰 방식이다([RFC 8292](https://www.rfc-editor.org/info/rfc8292/)).                                                                                                                                                          |
| D1          | `push_subscriptions` 테이블에 `user_id`, `endpoint`(unique), `p256dh`, `auth`, `expiration_time`, `user_agent`, `created_at`, `last_seen_at`, `revoked_at`을 저장한다. 엔드포인트는 요청을 보낼 수 있는 비밀 capability URL이므로 일반 사용자 응답이나 로그에 노출하지 않는다([MDN Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)).             |
| API         | 로그인 사용자만 구독 등록·갱신·해제를 호출한다. 동일 엔드포인트는 upsert하고, 계정 화면에서 브라우저별 구독 상태와 해제를 제공한다. 기존 CSRF·Origin 검사와 쓰기 Rate Limit을 그대로 적용한다.                                                                                                                                                                        |
| Worker 발송 | 인앱 알림 생성 뒤 사용자의 활성 구독으로 암호화 payload를 전송한다. VAPID 서명과 Web Push payload 암호화는 Worker Web Crypto(`crypto.subtle`) 또는 Cloudflare Worker 호환 라이브러리를 사용한다([Cloudflare Workers Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/)). Node 전용 `web-push` 패키지는 번들 호환성을 확인한 뒤 채택한다. |

### 10.3 알림 흐름과 안전 기준

1. 답글·멘션 등 이벤트가 발생하면 지금처럼 D1 `notifications` 행을 먼저 만든다.
2. 사용자가 푸시를 켠 경우에만 해당 사용자의 활성 구독을 조회해 Web Push를 시도한다. 자기 자신에게 발생한 이벤트, 뮤트·차단 대상, 사용자가 끈 알림 유형은 보내지 않는다.
3. 알림 payload에는 민감한 본문 전체를 넣지 않고 제목·짧은 안내·대상 글 URL만 넣는다. 자세한 내용은 클릭 후 인증된 사이트에서 읽는다.
4. 발송 응답이 404/410이면 구독을 폐기하고, 일시 오류는 제한된 횟수로 재시도한다. 대량 멘션과 다중 브라우저 구독에는 Worker 실행 시간·Rate Limit을 고려해 묶음 처리나 대기열이 필요하다.
5. 인앱 알림을 항상 남겨 푸시 권한 거부·브라우저 미지원·일시 발송 실패에도 활동 내역을 잃지 않게 한다.

| ------------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 설계안 문서화      | 완료     | VAPID secret 관리, D1 구독 스키마, 서비스 워커, 알림 유형별 opt-in에 관한 구현안을 이 문서에 정리했다. 브라우저 호환성이나 Worker 번들 호환성은 아직 실제 검증하지 않았다.                                                                                                                                                                                                                                            |
| 구독 관리 구현     | P1       | 서비스 워커 등록, 권한 요청, 구독 등록·갱신·해제 API와 계정 화면을 구현하고 중복 엔드포인트·권한 없는 요청을 검증한다.                                                                                                                                                                                                                                                                                                |
| 발송 연동          | P1       | 답글·멘션 인앱 알림과 Web Push를 연결하고 VAPID 서명, payload 암호화, 404/410 정리, 재시도·Rate Limit을 검증한다.                                                                                                                                                                                                                                                                                                     |
| 브라우저·운영 검증 | P1       | HTTPS 운영 환경에서 데스크톱 Chrome/Edge/Firefox·macOS Safari, Android Chrome, iOS/iPadOS 16.4 이상에서 홈 화면에 추가한 웹 앱을 대상으로 권한 허용·거부, 백그라운드 수신, 클릭 이동, 로그아웃·해제, 만료 구독 시나리오를 확인한다. Apple 플랫폼의 Web Push 대상은 [Apple 안내](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers)에 따라 검증한다. |

따라서 Web Push는 **추가 목표 P1로 채택 가능하지만 이번 P0 완료 항목에는 포함하지 않는다.** 우선 인앱 알림을 안정화한 뒤 구독 관리와 발송을 분리해 구현하고, 실제 운영 비밀 값과 기기별 수신 테스트가 끝났을 때 완료로 표시한다.
