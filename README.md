# mori.space

CY-Thread is a home for focused, welcoming communities. People gather around a shared interest, start conversations, and help one another grow. Community owners can shape a forum with its own categories, membership, and moderation rules.

## Product direction

The data model covers forums, categories, discussions, replies, memberships, roles, bans, reports, OAuth identities, sessions, bookmarks, and attachments. Threads and posts use soft deletion so authors and moderators can hide content without breaking reports or attachment history. The first product experience makes those ideas usable through:

- **Discover:** browse public Forums, active categories, and recent discussions across the platform.
- **Participate:** start a conversation, reply, follow a community, bookmark threads, and remove your own thread when needed.
- **Create:** request a new Forum for global admin approval, then manage its categories and appearance as its owner.
- **Keep it healthy:** report threads, review reports, pin or lock threads, and ban members from the community.

The home page is platform-wide and has no selected Forum. It loads public Forums, featured categories, and recent discussions from D1. Each Forum has its own thread list with search, categories, and inline WYSIWYG/Markdown writing. The local-only seed file supplies preview conversations. Google and CHZZK sign-in, posting, replies, following, thread bookmarks, community requests, profile name edits, category management, and basic moderation use authenticated server flows.

## Platform choices

- **Database: Cloudflare D1 + Drizzle.** The app runs on Cloudflare Workers and is at an early stage, so D1 removes the external PostgreSQL service and its connection management. D1 is Cloudflare's managed SQL option, but it uses SQLite semantics; this schema uses integer keys, millisecond timestamps, and boolean mappings. Current documented size caps are 500 MB per database on Free and 10 GB on Workers Paid. The Free plan includes 5 million rows read and 100,000 rows written per day; since September 1, 2026, D1 returns query errors after those daily limits are reached until reset. Paid includes 25 billion rows read and 50 million rows written monthly, then charges by usage. Each primary database serializes its own queries; D1 read replicas can spread reads, but this app's current plain Drizzle binding does not opt into the D1 Sessions API required to route through them ([limits](https://developers.cloudflare.com/d1/platform/limits/), [pricing](https://developers.cloudflare.com/d1/platform/pricing/), [read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/)). Revisit when query-latency and row-read metrics justify it. If PostgreSQL features or a larger single database become necessary, [Hyperdrive](https://developers.cloudflare.com/hyperdrive/) can pool Worker-to-Neon connections, but Neon remains the PostgreSQL host rather than becoming a Cloudflare-native database.
- **Files: Cloudflare R2.** Attachment metadata stays in D1 and image bytes go to R2. The editor accepts JPEG, PNG, GIF, and WebP images up to 5 MB and validates file signatures server-side. Published images are public; unattached uploads are visible only to their uploader while composing.
- **Framework: keep Nuxt + Vue for now.** Nuxt already targets [Cloudflare Workers](https://nuxt.com/deploy/cloudflare), and this project has a working Vue app, Toast UI editor, authentication and server routes. [SvelteKit's official Cloudflare adapter](https://svelte.dev/docs/kit/adapter-cloudflare) also supports Workers, bindings, local binding emulation and type generation; it is a viable alternative if the team prefers Svelte. The current Nuxt build's initial app chunk is roughly 134 kB before gzip; the rich editor is lazy-loaded and has a 361 kB largest chunk plus shared dependencies. A Svelte rewrite must replace the editor, auth and API integrations and then be benchmarked on identical routes and Worker bindings. There is no evidence yet that migrating would improve delivered performance enough to justify that rewrite.
- **Styling: Tailwind utilities and theme tokens plus class/ID selectors.** Shared palette, font families, focus rings, and page anchors use Tailwind. The component's class selectors keep the detailed responsive composition easy to tune.

The production build splits the rich editor and viewer from the initial page bundle. The most recent local build emitted an approximately 133 kB main page chunk; opening the composer or a thread loads editor/viewer chunks on demand. The largest lazy chunk is approximately 361 kB before gzip, with a 221 kB shared dependency chunk. Re-measure after editor or framework changes.

## Data model

The SQLite schema separates platform users/OAuth sessions from per-forum following and moderation. A forum owns categories and threads; a thread contains posts; reports track review decisions; R2 attachments point to a forum and optionally to a post. Composite keys prevent duplicate forum roles, follows, bans, and bookmarks. The feed, reply, and report lookups have dedicated indexes. Community member totals count the owner, moderators, followers, and people who have posted there, deduplicated by user ID.

## Cloudflare setup

Set `NUXT_PUBLIC_TURNSTILE_SITE_KEY` and `NUXT_TURNSTILE_SECRET_KEY` to enable Cloudflare Turnstile on thread, reply, report, and image-upload forms. The server verifies each one-use token before saving or storing an upload. Plain Nuxt development may omit these keys; the production Worker preview and deployment require the secret and site key.

Authenticated requests use Cloudflare Workers Rate Limiting bindings keyed by user ID: 10 thread/post writes, 6 image uploads, 5 reports, 2 community creations, 30 moderation actions, 2 abandoned-upload cleanups, 60 other writes, and 120 thread/feed reads per minute. Anonymous thread reads use Cloudflare's `cf-connecting-ip` as the key at 120 per minute. Requests over a limit receive HTTP 429 with `Retry-After: 60`. The limits are separate per action class. Cloudflare enforces these counters per data-center location with eventual consistency, so they are abuse throttles rather than exact global quotas. The numeric `namespace_id` values in `wrangler.toml` must remain unique within the Cloudflare account; change them if another Worker already uses one. `npm run dev:worker` uses Wrangler's local binding simulation.

The app Worker has Workers Logs enabled with 100% sampling. The `server/plugins/observability.ts` hook writes structured warning logs for 429 responses and error logs for 5xx responses. After deployment, inspect them under Workers & Pages → `community` → Observability → Logs; Workers Logs currently retain 3 days on Free or 7 days on Paid, and extra volume can be billed on Paid. Use `npx wrangler tail community` for live troubleshooting.

## Forum discovery and approval

The home page shows up to eight active Threads collections (categories) in a four-column grid on desktop. The `community` Worker receives a Cloudflare Cron Trigger at minute 0 every hour through Nitro's `cloudflare:scheduled` hook. It ranks public categories by non-deleted posts created in the last 24 hours and writes the top eight to `featured_categories` in D1. Until its first successful run, the home endpoint falls back to the first eight public categories. The `/explore` page searches category names and addresses across public Forums, with a Forum filter.

Creating a Forum now submits a request. An account with `users.is_global_admin = 1` reviews requests at `/admin/forum-requests`; approval creates the Forum, its owner, and its starter categories together. A Forum owner or appointed admin can create, rename, and delete categories. Deleting a populated category requires choosing another category in the same Forum; all of its posts, including hidden posts, move in one D1 transaction. Global admins inherit Forum moderation and appointment powers and cannot be banned by Forum staff. After the first trusted account has signed in, bootstrap it with `npx wrangler d1 execute community --remote --command "UPDATE users SET is_global_admin = 1 WHERE email = 'admin@example.com'"`, replacing the address with that account's email. For a CHZZK-only account without an email address, use `UPDATE users SET is_global_admin = 1 WHERE id IN (SELECT user_id FROM oauth_accounts WHERE provider = 'chzzk' AND provider_user_id = '<channel-id>')` after verifying the channel ID. Only an existing global admin can approve new Forums.

The global dashboard at `/admin` summarizes users, Forums, visible threads and posts, open reports, and pending Forum requests. Its 30-day activity chart uses UTC calendar days and counts currently visible content; active members are distinct authors of visible threads or posts in that period. The searchable Forum list shows each Forum's owner, content totals, open reports, and a link to its moderation page. These are content and moderation metrics from D1; page views and visitor traffic are not recorded.

Global admins can open `/admin/users` from the home header's `관리도구` button. The paginated user list searches names, email addresses, authored thread titles, and post text. Each user page shows recent threads and comments with search and pagination, plus an audit history of account suspensions. Admins can suspend accounts for 30 minutes, 1 hour, 6 hours, 1 day, 7 days, 1 month, or permanently, and lift suspensions. Active suspensions block authenticated API writes across Forums while allowing reading and logout. The suspended account sees the reason and end time in a site-wide banner. Apply migration `0008_user_suspensions.sql` before deploying this code.

Forum owners and admins can open `/forums/<slug>/admin/settings` from their Forum management menu. They can change the Forum name, description, square text icon, icon colors, and scoped color variables. The CSS editor accepts only `--forum-accent`, `--forum-canvas`, `--forum-surface`, `--forum-text`, `--forum-muted`, and `--forum-border` with six-digit hex colors; these values are applied only within that Forum's pages. The home feed now loads actual public Forums, categories, threads, and D1 counts rather than placeholder content.

The header theme selector stores White, Dark, or System preference in the browser. A Forum admin can disable dark mode for their Forum in settings; that Forum then uses White even when the saved preference or OS is Dark. Forum pages share an account-aware header, and their new-thread composer uses the existing Toast UI WYSIWYG/Markdown editor. CHZZK sign-in redirects accounts without an email to `/account/email`. The entered address is saved as an unverified contact email, separate from the verified Google identity email, so it cannot take over or automatically link a Google account. For privileged owner and moderator assignments, use the CHZZK user's numeric ID; email-based assignments use verified Google addresses. Apply migration `0009_chzzk_contact_email.sql` before deploying this version.

Published images keep their D1 visibility/deletion check on every request, then use Cloudflare's local Cache API to serve repeat image bytes without another R2 read. Pending uploads are not cached. Browsers cache published images for 60 seconds and the edge cache keeps them for up to one hour. The Cache API is local to each data center, so the first request in another location may still read R2.

## Backups and recovery

D1 Time Travel provides point-in-time recovery for 7 days on Free and 30 days on Paid. For longer recovery, a separate Worker in `backup/` runs every day at 02:00 Korea time: it exports D1 through the D1 REST API and copies all R2 images into a dated snapshot. Complete snapshots are kept for 31 days in a private `community-backups` bucket. The backup uses a D1 API token and separate Worker so the public app Worker cannot write to the archive.

To enable scheduled backups, create the private destination bucket with `npx wrangler r2 bucket create community-backups`, then configure `ACCOUNT_ID` and a narrowly scoped D1 export token with `npx wrangler secret put ACCOUNT_ID --config backup/wrangler.toml` and `npx wrangler secret put D1_REST_API_TOKEN --config backup/wrangler.toml`. Deploy the backup Worker with `npx wrangler deploy --config backup/wrangler.toml`. Trigger a first run with `npx wrangler workflows trigger community-backup-workflow --config backup/wrangler.toml` and confirm a `manifest.json` appears in the backup bucket before relying on the schedule. The backup Workflow has separate Workers Logs enabled so failures can be checked in Observability.

To recover images, run `node scripts/restore-r2-snapshot.mjs YYYY-MM-DD --apply-r2`; the script downloads the D1 SQL export and asks you to type `RESTORE` before it writes archived image keys back to the live `community` bucket. It leaves newer or unlisted image keys untouched. For D1, create a new empty restore database, import the resulting `restore-YYYY-MM-DD/database.sql` with `wrangler d1 execute <restore-database> --remote --file=...`, verify the restored application, and then point the app Worker at that database. Do not import a full snapshot over a populated D1 database. Run and verify a restore drill before treating these backups as a recovery guarantee.

The app uses D1 through the Worker `DB` binding and Drizzle. For one-off administrative SQL in place of a `psql` connection, use Wrangler's D1 command, for example `npx wrangler d1 execute community --remote --command "SELECT count(*) AS forums FROM forums"`. D1 uses SQLite SQL and does not expose a PostgreSQL wire endpoint; use Hyperdrive only if retaining a PostgreSQL host such as Neon is intentional.

1. Install dependencies and authenticate Wrangler: `npm install`, then `npx wrangler login`.
2. The `community` D1 database and matching R2 bucket are bound in `wrangler.toml`. Before deploying code with pending schema migrations, apply them with `npm run db:migrate:remote`. To provision an independent account, use `npm run db:create`, replace `database_id` with the ID Wrangler returns, and create the R2 bucket with `npx wrangler r2 bucket create community`.
3. Apply schema locally with `npm run db:migrate:local`; optionally load preview-only rows with `npm run db:seed:local`. Neon is a development database and its existing data is intentionally not imported.
4. Start the Worker with bindings using `npm run dev:worker` (this builds first). `npm run dev` runs the Nuxt development server without local Cloudflare bindings.
5. For local sign-in, create an ignored `.dev.vars` file with `NUXT_SESSION_PASSWORD` (at least 32 random characters). Add `NUXT_OAUTH_GOOGLE_CLIENT_ID` and `NUXT_OAUTH_GOOGLE_CLIENT_SECRET` for Google, or `NUXT_OAUTH_CHZZK_CLIENT_ID` and `NUXT_OAUTH_CHZZK_CLIENT_SECRET` for CHZZK. Add the Turnstile keys there too when testing writes in `wrangler dev`. Register `http://localhost:8787/api/auth/google` for Google and `http://localhost:8787/api/auth/chzzk/callback` for CHZZK when using the default Wrangler port. The CHZZK application needs the user information scope.
6. Before deploying, apply migrations with `npm run db:migrate:remote`. Set `NUXT_SESSION_PASSWORD`, `NUXT_TURNSTILE_SECRET_KEY`, and the chosen OAuth provider credentials with `npx wrangler secret put <NAME>`. Register `https://<your-worker-domain>/api/auth/chzzk/callback` as the CHZZK redirect URI; the Worker computes this URI from the incoming request origin. Configure `NUXT_PUBLIC_TURNSTILE_SITE_KEY` as a Worker variable, then deploy with `npx wrangler deploy`. Set the Google OAuth redirect URI to `https://<your-worker-domain>/api/auth/google` in Google Cloud Console.

## Data protection

D1 Time Travel is enabled automatically. It can restore to a point within 7 days on Workers Free or 30 days on Workers Paid; restore replaces the live database, so follow Cloudflare's confirmation and recovery guidance carefully ([Time Travel and backups](https://developers.cloudflare.com/d1/reference/time-travel/)). For an independent SQL export before a risky migration, run `npm run db:backup:remote`. This writes `community-backup.sql`, which Git ignores because it contains database records. Store the export encrypted outside the checkout and periodically verify that it can be restored into a separate empty D1 database. A D1 export contains SQL data only; R2 image objects need a separate backup/copy plan. The backup command has not been run against production in this task.

The session is stored in Nuxt Auth Utils' sealed, HTTP-only cookie. D1 stores user profiles and Google or CHZZK provider IDs; OAuth access tokens are not persisted. CHZZK login reads the authenticated user's channel ID, then retrieves the matching public channel name and image with application credentials. The browser can read the current session profile but cannot change its identity. The editor stores Markdown; the server also stores escaped HTML fallback content. Forum approval, profile name editing, category creation/editing, author/moderator thread deletion, reports, thread moderation, basic bans, and moderator cleanup for R2 uploads older than 24 hours are implemented. Private/follower-only visibility policies remain follow-up work.

The app's shared visual system lives in `app/assets/css/main.css`; the homepage is under `app/pages/index.vue`. Dedicated pages are available at `/login`, `/forums/<slug>/threads`, `/forums/<slug>/threads/<id>`, `/forums/<slug>/admin`, `/forums/<slug>/admin/categories`, `/forums/<slug>/admin/users`, and `/forums/<slug>/reports`. Members can create, edit, and soft-delete threads and posts, reply in a two-level comment tree, and report threads or individual posts. Search supports title/body text, categories, pinned/locked filters, sorting, and pagination. Moderator tools include thread pin/lock/hide, member lookup and bans, report review, category settings, moderator appointments, current totals, active-member counts, open-report counts, and a 30-day activity chart. Only owners can appoint admins; owners and admins can appoint/remove moderators, enforced by server routes as well as the interface.

Wrangler commands use an active `npx wrangler login` OAuth session; a separate Cloudflare API token is not needed for remote D1 migrations, exports, or deployment while that session remains valid. If it expires, log in again. The Drizzle Kit `d1-http` driver is the exception: operations that directly access remote D1 through Drizzle Kit require `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID`, and `CLOUDFLARE_D1_TOKEN`. Routine schema generation and the documented Wrangler migration workflow do not use that token. Keep any token in local environment or a secret manager, never in source control.

The old Neon connection URL was stored in the tracked Wrangler configuration. It has been removed, but deleting it from the current version does not remove it from Git history. Rotate that database password before reusing Neon or Hyperdrive, and consider purging the old secret from repository history before making the repository public. The provisioned D1 is schema-only by choice; no historical data import is needed. Production CHZZK sign-in needs an issued CHZZK application Client ID and Client Secret, its registered callback URL, and the matching Worker settings. Posting also requires Turnstile keys.
