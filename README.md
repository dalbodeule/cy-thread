# mori.space

CY-Thread is a home for focused, welcoming communities. People gather around a shared interest, start conversations, and help one another grow. Community owners can shape a forum with its own categories, membership, and moderation rules.

## Product direction

The D1 schema covers Forum requests and featured categories; forums, categories, threads, posts, memberships, roles, bans, and reports; user accounts, OAuth identities, suspensions, blocks, and mutes; bookmarks, reactions, polls, notifications, thread subscriptions, and read positions; mail campaigns and their outbox; moderation logs; and attachments. Login sessions are kept in Nuxt Auth Utils' sealed cookie rather than D1. A legacy `sessions` table remains in the Drizzle schema and initial migration, but the application does not read or write it. Threads and posts use soft deletion so authors and moderators can hide content without breaking reports or attachment history. The product makes those ideas usable through:

- **Discover:** browse public Forums, active categories, and recent discussions across the platform.
- **Participate:** search public discussions site-wide, follow Forums, subscribe to threads, get notifications for comment replies and `@name` mentions, bookmark or react to content, and review your activity and saved posts.
- **Create:** request a new Forum for global admin approval, then manage its categories and appearance as its owner.
- **Keep it healthy:** report threads, review moderation history, pin or lock threads, configure keyword blocking rules, and block users or mute Forums.

The home page is platform-wide and has no selected Forum. It loads public Forums, featured categories, and recent discussions from D1. Each Forum has its own thread list with search, categories, and inline WYSIWYG/Markdown writing. Public and approval-only private Forums are supported; their owners can configure access, comment rules, keyword blocking terms, and resource links. In public Forums, comment access can allow guests, any signed-in user, or approved Forum members; Forum staff bypass this membership-level setting. Private Forums still require approved access to read and comment, regardless of the comment-access setting. Matching keywords reject new Threads and replies with HTTP 422; this check runs on creation, not when existing content is edited, and it creates no moderation queue or case record. The local-only seed file supplies preview conversations. Google and CHZZK sign-in, authenticated thread creation, following, thread bookmarks and subscriptions, reactions, community requests, profile name edits, public profiles, account data export, category management, and moderation run through server routes with permissions checked for each action.

## Platform choices

- **Database: Cloudflare D1 + Drizzle.** The app runs on Cloudflare Workers and is at an early stage, so D1 removes the external PostgreSQL service and its connection management. D1 is Cloudflare's managed SQL option, but it uses SQLite semantics; this schema uses integer keys, millisecond timestamps, and boolean mappings. Current documented size caps are 500 MB per database on Free and 10 GB on Workers Paid. The Free plan includes 5 million rows read and 100,000 rows written per day; since September 1, 2026, D1 returns query errors after those daily limits are reached until midnight UTC. Paid includes 25 billion rows read and 50 million rows written monthly, then charges by usage. Each primary database serializes its own queries; D1 read replicas can spread reads, but this app's current plain Drizzle binding does not opt into the D1 Sessions API required to route through them ([limits](https://developers.cloudflare.com/d1/platform/limits/), [pricing](https://developers.cloudflare.com/d1/platform/pricing/), [read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/), [September 1, 2026 limit enforcement](https://developers.cloudflare.com/changelog/post/2026-09-01-d1-free-tier-limit-enforcement/)). Revisit when query-latency and row-read metrics justify it. If PostgreSQL features or a larger single database become necessary, [Hyperdrive](https://developers.cloudflare.com/hyperdrive/) can pool Worker-to-Neon connections, but Neon remains the PostgreSQL host rather than becoming a Cloudflare-native database.
- **Files: Cloudflare R2.** Attachment metadata stays in D1 and image bytes go to R2. The editor accepts JPEG, PNG, GIF, and WebP images up to 5 MB and validates file signatures server-side. Images in public Forums are public; images in private Forums require approved membership, owner access, Forum staff access, or global admin access. An unattached upload is visible only to its uploader, who must also still have permission to read that Forum.
- **Framework: keep Nuxt + Vue for now.** Nuxt already targets [Cloudflare Workers](https://nuxt.com/deploy/cloudflare), and this project has a working Vue app, Toast UI editor, authentication and server routes. [SvelteKit's official Cloudflare adapter](https://svelte.dev/docs/kit/adapter-cloudflare) also supports Workers, bindings, local binding emulation and type generation; it is a viable alternative if the team prefers Svelte. The rich editor is lazy-loaded. A Svelte rewrite must replace the editor, auth and API integrations and then be benchmarked on identical routes and Worker bindings. There is no evidence yet that migrating would improve delivered performance enough to justify that rewrite.
- **Styling: Tailwind theme tokens and utilities alongside regular CSS selectors.** `tailwind.config.ts` defines the shared palette and font stacks, and `@apply` uses Tailwind utilities for shared styling and focus rings. Page-anchor scroll offsets and detailed responsive composition are defined with regular CSS selectors.

The production build splits the rich editor and viewer from the initial page bundle; opening the composer or a thread loads those chunks on demand. Chunk sizes vary with source and dependency versions, so use the output of `npm run build` when comparing a change rather than treating old local build sizes as current measurements.

## Data model

The SQLite schema separates platform users and OAuth identity records from per-forum following and moderation; login sessions themselves stay in sealed cookies. The schema still defines a legacy `sessions` table, but authentication does not use it. A forum owns categories and threads; a thread contains posts and a view counter; reports track review decisions; R2 attachments point to a forum and optionally to a post. Composite keys prevent duplicate forum roles, follows, bans, and bookmarks. The feed, reply, and report lookups have dedicated indexes. Community member totals count the owner, appointed Forum admins and moderators, approved members, followers, and accounts that authored non-deleted threads or posts, deduplicated by user ID.

## Cloudflare setup

Set `NUXT_PUBLIC_TURNSTILE_SITE_KEY` and `NUXT_TURNSTILE_SECRET_KEY` to enable Cloudflare Turnstile on Forum creation requests, thread and reply creation, reports, private-Forum membership requests, and Forum post-image uploads. Profile-photo uploads do not use Turnstile. The server verifies each one-use token before accepting a protected request or storing a post-image upload. Plain Nuxt development may omit these keys; the production Worker preview and deployment require the secret and site key.

The public Forum list, global category list, featured categories, and Forum thread list/detail reads use the Cloudflare Workers Rate Limiting binding at 120 requests per minute. Authenticated requests to these endpoints are keyed by user ID; anonymous requests use `cf-connecting-ip`, and skip rate limiting if Cloudflare does not provide that header. Other authenticated API reads are not rate-limited by this middleware. The thread-view count POST endpoint also uses the 120-per-minute read binding, keyed by user ID or client IP. Authenticated writes use separate bindings keyed by user ID: 10 thread creations, replies, and thread/post edits; 6 image uploads; 5 reports; 2 community creations; 30 Forum moderation actions and platform account suspensions; 2 abandoned-upload cleanups; and 60 other writes per minute. Unauthenticated writes, including guest replies where the Forum allows them, do not use these write limiter bindings. The thread read endpoints are rate-limited regardless of Forum visibility. Requests over a limit receive HTTP 429 with `Retry-After: 60`. Cloudflare enforces these counters per data-center location with eventual consistency, so they are abuse throttles rather than exact global quotas. If a configured limiter's `limit()` call fails, the middleware logs the error and allows the request; if a binding is missing outside plain development mode, it returns HTTP 503 instead. The numeric `namespace_id` values in `wrangler.toml` must remain unique within the Cloudflare account; change them if another Worker already uses one. `npm run dev:worker` uses Wrangler's local binding simulation.

The app Worker has Workers Logs enabled with 100% sampling. The `server/plugins/observability.ts` hook adds an `app` duration to `Server-Timing`, logs responses taking at least one second, writes structured warning logs for 429 responses, and error logs for 5xx responses. After deployment, inspect them under Workers & Pages → `community` → Observability → Logs; Workers Logs currently retain 3 days on Free or 7 days on Paid, and extra volume can be billed on Paid. Cloudflare plans to move Workers Logs to its Observability pricing on December 1, 2026, so recheck retention and billing then ([Workers Logs pricing](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)). Use `npx wrangler tail community` for live troubleshooting.

## Forum discovery and approval

The home page shows up to 100 public Forums in alphabetical order; its local name/description/slug search only filters that returned set and does not paginate. It also shows up to eight public categories ranked by non-deleted posts from the last 24 hours in a four-column grid on desktop. If fewer than eight categories have recent posts, categories with no recent activity can fill the remaining slots. The heading says “활발한 카테고리” when at least one result has recent activity and “카테고리 둘러보기” otherwise. The `community` Worker receives a Cloudflare Cron Trigger at minute 0 every hour through Nitro's `cloudflare:scheduled` hook and writes the ranking to `featured_categories` in D1. That hourly event also removes up to 100 unattached thread images older than 24 hours, removes up to 100 images from posts deleted for at least 30 days, and scans uploaded avatars for keys no longer referenced by a user; failed deletion rows/objects are retried on later hourly runs. A separate every-minute Cron Trigger processes queued email campaigns. If the featured-category query returns no public rows, the home endpoint falls back to the first eight public categories. The `/explore` page searches category names and slugs across public Forums, with a Forum filter, returning 30 results at a time with a load-more control; its Forum filter options use the same first 100 alphabetically ordered public Forums.

Creating a Forum now submits a request. An account with `users.is_global_admin = 1` reviews requests at `/admin/forum-requests`; approval creates the Forum, its owner, and its starter categories together. A Forum owner, appointed admin, or global admin can create, rename, and delete categories. Deleting a populated category requires choosing another category in the same Forum; all of its Thread rows, including soft-deleted ones, move in one D1 batch, while their body and comments remain attached to those Threads. Forum owners and global admins can appoint or remove Forum admins; owners, Forum admins, and global admins can appoint or remove moderators. Global admins inherit Forum management and moderation powers. Forum staff cannot ban the Forum owner or a global admin; moderators cannot ban fellow moderators, and only the owner or a global admin can manage Forum admin accounts. After the first trusted account has signed in, bootstrap it with `npx wrangler d1 execute community --remote --command "UPDATE users SET is_global_admin = 1 WHERE email = 'admin@example.com'"`, replacing the address with that account's email. For a CHZZK-only account without an email address, use `UPDATE users SET is_global_admin = 1 WHERE id IN (SELECT user_id FROM oauth_accounts WHERE provider = 'chzzk' AND provider_user_id = '<channel-id>')` after verifying the channel ID. Only an existing global admin can approve new Forums.

The global dashboard at `/admin` summarizes users, Forums, non-deleted threads and posts across public and private Forums, open reports, and pending Forum requests. Its 30-day activity chart uses UTC calendar days and counts non-deleted content; active members are distinct account authors of non-deleted threads or posts created in that period. The searchable Forum list shows each Forum's owner, content totals, open reports, and a link to its moderation page. The dashboard has no aggregate visitor-traffic metric. Thread detail views are counted once per browser-tab session and shown on thread pages and recent-thread lists; this is not a count of unique people or a full analytics system.

Global admins can open `/admin/users` from the home header's `관리도구` button. The paginated user list searches names, email addresses, authored thread titles, and post text. Each user page shows recent threads and comments with search and pagination (20 items per page), plus the latest 10 suspension records. Admins can suspend accounts for 30 minutes, 1 hour, 6 hours, 1 day, 7 days, 1 month, or permanently, and lift suspensions. A global admin cannot be suspended, and an admin cannot suspend their own account. Active suspensions block authenticated API mutations across the site, except logout, while read requests remain available. The suspended account sees the reason and expiry time, or permanent status, in a site-wide banner. Apply all pending D1 migrations before deploying this code.

Forum owners, admins, and global admins can open `/forums/<slug>/admin/settings` from their Forum management menu. They can change the Forum name, description, square text icon, icon colors, and scoped color variables, and configure public/private approval access, comment access, rules, welcome text, keyword blocking terms, and resource links. Resource links appear to everyone on public Forums and to approved members, owners, Forum admins and moderators, and global admins on private Forums. The CSS editor accepts only `--forum-accent`, `--forum-canvas`, `--forum-surface`, `--forum-text`, `--forum-muted`, and `--forum-border` with six-digit hex colors; these values are applied only within that Forum's pages. The home feed loads public Forums, categories, threads, and D1 counts from D1.

The header theme selector stores White, Dark, or System preference in the browser. A Forum admin can disable dark mode for their Forum in settings; that Forum then uses White even when the saved preference or OS is Dark, and hides its theme selector. Forum pages share an account-aware header, and their new-thread composer uses the existing Toast UI WYSIWYG/Markdown editor. CHZZK sign-in redirects accounts without an email to `/account/email`. The entered address is saved as an unverified contact email, separate from the verified Google identity email, so it cannot take over or automatically link a Google account. For privileged owner and moderator assignments, use the CHZZK user's numeric ID; email-based assignments use verified Google addresses. Apply all pending D1 migrations before deploying this code.

Images keep their D1 visibility/deletion check on cache misses, then use Cloudflare's Cache API for repeat reads of public Forum image bytes without another R2 read. Workers Cache is enabled for responses explicitly marked public; all other app responses default to `private, no-store`, and personalized thread APIs are not cached. Published public images have a 60-second shared-cache lifetime; private Forum images and unattached uploads are never marked public. A cached image may remain visible for up to 60 seconds after its Forum becomes private or the post is deleted.

## Observability

The app Worker's observability settings in `wrangler.toml` keep application error logs at full sampling, disable per-request invocation logs, and sample traces at 5%. Cloudflare Issues is enabled for failed invocations and HTTP 5xx responses. Slow responses and rate-limited responses are logged at 10% and 1% respectively; those sampled events include `sampleRate` and should not be counted as complete totals. Error objects are reduced to a bounded name and message with URLs and email addresses redacted. The separate backup Worker keeps full logging so scheduled backup failures remain visible. Review account-level ingestion and storage in Cloudflare Billable Usage after deployment, and adjust trace sampling if necessary.

## Backups and recovery

D1 Time Travel provides point-in-time recovery for 7 days on Free and 30 days on Paid. For longer recovery, a separate Worker in `backup/` runs every day at 02:00 Korea time (17:00 UTC): it exports D1 through the D1 REST API and copies every R2 object under `forums/` into a dated snapshot. Snapshot dates and prefixes use the UTC calendar date from the scheduled event timestamp, so a run at 02:00 Korea time is labeled with the previous calendar date in Korea. Uploaded profile avatars under `avatars/` are not included; after restoring a snapshot without those objects, an affected profile may show the user's initial until the avatar is re-uploaded or changed to another source. The private `community-backups` bucket is pruned after each successful run by deleting the UTC date prefix exactly 31 days before that snapshot date. If a scheduled run is missed on an expiry date, older snapshots can remain in the bucket. The backup uses a D1 API token and separate Worker so the public app Worker cannot write to the archive.

To enable scheduled backups, create the private destination bucket with `npx wrangler r2 bucket create community-backups`, then configure `ACCOUNT_ID` and a narrowly scoped D1 export token with `npx wrangler secret put ACCOUNT_ID --config backup/wrangler.toml` and `npx wrangler secret put D1_REST_API_TOKEN --config backup/wrangler.toml`. Deploy the backup Worker with `npx wrangler deploy --config backup/wrangler.toml`. Trigger a first run with `npx wrangler workflows trigger community-backup-workflow --config backup/wrangler.toml` and confirm a `manifest.json` appears in the backup bucket before relying on the schedule. The backup Workflow has separate Workers Logs enabled so failures can be checked in Observability.

To recover Forum attachments, pass the snapshot's UTC date from its manifest: `node scripts/restore-r2-snapshot.mjs YYYY-MM-DD --apply-r2`. The script downloads the D1 SQL export and asks you to type `RESTORE` before it writes archived `forums/` keys back to the live `community` bucket. Keys present in the snapshot are overwritten even if the live object has newer contents; keys absent from the snapshot are left untouched. Uploaded `avatars/` are outside this snapshot and are not restored. For D1, create a new empty restore database, import the resulting `restore-YYYY-MM-DD/database.sql` with `wrangler d1 execute <restore-database> --remote --file=...`, verify the restored application, and then point the app Worker at that database. Do not import a full snapshot over a populated D1 database. Run and verify a restore drill before treating these backups as a recovery guarantee.

The app uses D1 through the Worker `DB` binding and Drizzle. For one-off administrative SQL in place of a `psql` connection, use Wrangler's D1 command, for example `npx wrangler d1 execute community --remote --command "SELECT count(*) AS forums FROM forums"`. D1 uses SQLite SQL and does not expose a PostgreSQL wire endpoint; use Hyperdrive only if retaining a PostgreSQL host such as Neon is intentional.

1. Install dependencies and authenticate Wrangler: `npm install`, then `npx wrangler login`.
2. The `community` D1 database and matching R2 bucket are bound in `wrangler.toml`. Before deploying code with pending schema migrations, apply them with `npm run db:migrate:remote`. To provision an independent account, use `npm run db:create`, replace `database_id` with the ID Wrangler returns, and create the R2 bucket with `npx wrangler r2 bucket create community`.
3. Apply schema to Wrangler's local D1 database with `npm run db:migrate:local`; optionally load preview-only rows with `npm run db:seed:local`. The previous Neon database is no longer used by this code, and its data has not been imported into D1.
4. Start the Worker with bindings using `npm run dev:worker` (this builds first). `npm run dev` runs the Nuxt development server without local Cloudflare bindings.
5. For local sign-in, create an ignored `.dev.vars` file with `NUXT_SESSION_PASSWORD` (at least 32 random characters). Add `NUXT_OAUTH_GOOGLE_CLIENT_ID` and `NUXT_OAUTH_GOOGLE_CLIENT_SECRET` for Google, or `NUXT_OAUTH_CHZZK_CLIENT_ID` and `NUXT_OAUTH_CHZZK_CLIENT_SECRET` for CHZZK. Add the Turnstile keys there too when testing writes in `wrangler dev`. Register `http://localhost:8787/api/auth/google` for Google and `http://localhost:8787/api/auth/chzzk/callback` for CHZZK when using the default Wrangler port. The CHZZK application needs the user information scope.
6. Before deploying, apply migrations with `npm run db:migrate:remote`. Set `NUXT_SESSION_PASSWORD`, `NUXT_TURNSTILE_SECRET_KEY`, and the chosen OAuth provider credentials with `npx wrangler secret put <NAME>`. Register `https://<your-worker-domain>/api/auth/chzzk/callback` as the CHZZK redirect URI; the Worker computes this URI from the incoming request origin. Configure `NUXT_PUBLIC_TURNSTILE_SITE_KEY` as a Worker variable, then deploy with `npx wrangler deploy`. Set the Google OAuth redirect URI to `https://<your-worker-domain>/api/auth/google` in Google Cloud Console.

## Data protection

D1 Time Travel is enabled automatically. It can restore to a point within 7 days on Workers Free or 30 days on Workers Paid; restore replaces the live database, so follow Cloudflare's confirmation and recovery guidance carefully ([Time Travel and backups](https://developers.cloudflare.com/d1/reference/time-travel/)). For an independent SQL export before a risky migration, run `npm run db:backup:remote`. This writes `community-backup.sql`, which Git ignores because it contains database records. Store the export encrypted outside the checkout and periodically verify that it can be restored into a separate empty D1 database. A D1 export contains SQL data only; R2 image objects need a separate backup/copy plan. Having the command configured does not mean a backup has been taken or a restore verified.

The session is stored in Nuxt Auth Utils' sealed, HTTP-only cookie. D1 stores user profiles and Google or CHZZK provider IDs. The current OAuth callbacks do not read stored provider tokens or write access/refresh tokens to D1; the CHZZK callback uses its provider-issued access token in memory to fetch the user's profile. Nullable legacy token columns remain in the `oauth_accounts` schema and initial migration, so check existing database values separately before assuming they are empty. CHZZK login reads the authenticated user's channel ID, then retrieves the matching public channel name and image with application credentials. The browser can read the current session profile but cannot change its identity. The editor and viewer use Markdown. Write routes also store an `html_sanitized` value made from escaped text wrapped in paragraph and line-break tags, but current read and display code does not use that column. Forum approval, public/private membership, profile name editing, category creation/editing, author/moderator thread deletion, reports, thread moderation, temporary and permanent account suspensions, user blocks, Forum mutes, public profiles, account data export (up to 1,000 authored Threads, 5,000 Posts, and 1,000 submitted reports), resource links, and moderation history are implemented. Followers-only Forum visibility and a self-service account deletion flow remain follow-up work.

The app's shared visual system lives in `app/assets/css/main.css`; the homepage is under `app/pages/index.vue`. Dedicated pages include `/login`, `/search`, `/explore`, `/following`, `/policies`, `/account/profile`, `/account/email`, `/account/verify-email`, `/admin`, `/admin/forum-requests`, `/admin/users`, `/admin/users/<userId>`, `/admin/mail`, `/forums/request`, `/forums/<slug>/threads`, `/forums/<slug>/threads/<id>`, `/forums/<slug>/admin`, `/forums/<slug>/admin/categories`, `/forums/<slug>/admin/settings`, `/forums/<slug>/admin/users`, `/forums/<slug>/admin/mail`, `/forums/<slug>/admin/logs`, `/forums/<slug>/reports`, `/users/<userId>`, and `/mail/unsubscribe`. Authors can create and edit their own threads and posts, and soft-delete their own threads and replies; Forum moderators can moderate content in their Forum. The root post that stores a thread body cannot be deleted independently: deleting the thread soft-deletes its body and comments together. Members can reply in a two-level comment tree and report threads or individual posts. Search supports title/body text, Forum and category filters, a start date, and relevance/latest sorting. Each matching thread appears once, even if several of its posts match. The page shows the first 30 results; the API accepts `limit` (up to 50) and `offset`, but the page does not yet provide pagination controls. Forum operating pages provide thread pin/lock/hide, member lookup and bans, report review, current totals, active-member counts, open-report counts, and a 30-day activity chart. Category settings, Forum mail, and moderator appointments are limited to Forum owners and admins (and global admins); moderators can handle reports and content moderation but cannot use those management controls. Forum owners and global admins can appoint Forum admins; owners and Forum admins can appoint or remove moderators, while global admins inherit both sets of powers. Server routes enforce these role limits in addition to the interface.

Wrangler commands use an active `npx wrangler login` OAuth session; a separate Cloudflare API token is not needed for remote D1 migrations, exports, or deployment while that session remains valid. If it expires, log in again. The Drizzle Kit `d1-http` driver is the exception: operations that directly access remote D1 through Drizzle Kit require `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID`, and `CLOUDFLARE_D1_TOKEN`. Routine schema generation and the documented Wrangler migration workflow do not use that token. Keep any token in local environment or a secret manager, never in source control.

The old Neon connection URL was stored in the tracked Wrangler configuration. It has been removed, but deleting it from the current version does not remove it from Git history. Rotate that database password before reusing Neon or Hyperdrive, and consider purging the old secret from repository history before making the repository public. The provisioned D1 is schema-only by choice; no historical data import is needed. Production CHZZK sign-in needs an issued CHZZK application Client ID and Client Secret, its registered callback URL, and the matching Worker settings. Posting also requires Turnstile keys.

## Development

```sh
npm install
npm run dev
```

Build the Cloudflare deployment bundle with `npm run build`.

For a quick HTTP response baseline, set `PERF_BASE_URL`, optionally comma-separated `PERF_PATHS`, and optionally `PERF_ITERATIONS` (1–100, default 5), then run `npm run perf:baseline`. It prints p50/p95 response-completion times, decoded response-body bytes, `Cf-Cache-Status`, `Cache-Control`, content encoding, and server timing to stdout as a table and JSON; it does not write a file. Requests run sequentially, so later samples can show warm-cache behavior. The byte count excludes headers and compressed wire size, and the script does not measure page rendering or follow-up asset chunks. Connection failures and non-2xx responses produce a nonzero exit code. The defaults target `http://localhost:8787/`, `/explore`, and `/search`.
